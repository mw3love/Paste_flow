## 한눈에

두 백지 설계는 서로를 보지 않고도 같은 답을 냈다: **C# + WPF**, 순수 로직(Core)과 Windows 연결부를 나눈 구조, SQLite에 이미지는 파일로 따로, 300줄 파일 제한을 검사로, 단일 설치 파일 + 자동 업데이트(Velopack). 둘 다 2등 언어로 파이썬을 꼽지 않았다(Claude는 Rust, GPT는 C++/Qt).

지금 PasteFlow와 갈리는 곳은 여섯 칸 전부다. 다만 **언어·화면 도구는 통째로 다시 쓰는 일**(약 2만 줄)이고, **폴더 구조·데이터 저장·시험과 검사는 파이썬을 그대로 두고도 백지안의 핵심을 가져올 수 있다.**

## 언어 — 백지 설계 2판 (TypeScript 후보를 넣어 다시)

사용자가 「TypeScript도 고려했나」를 물었다. 1판 두 설계는 TypeScript를 한 줄씩만 다뤘다(Claude: Electron은 메모리 초과, GPT: Rust 핵심부 + JS 화면은 두 언어 관리 비용). 그래서 [질의서 2판](20261116-설계질의서-2.md)에 후보 넷(C# · Rust+TypeScript(Tauri) · TypeScript만(Electron) · C++)을 표로 비교하라고 넣어 다시 받았다: [Claude 2판](20261116-백지설계-2-claude.md) · [GPT 2판](20261116-백지설계-2-gpt.md).

| 후보 | 크기(추정) | 쉴 때 메모리(추정) | AI가 고치기 | 두 설계 평가 |
|---|---|---|---|---|
| C# + WPF | 런타임 포함 70~160MB · 런타임 따로 약 5MB | 40~100MB | 가장 유리 | Claude 1등 · GPT 2등 |
| C++ + Qt | 1~90MB | 10~60MB | 불리(메모리·스레드 오류가 컴파일 통과) | GPT 1등 · Claude 하위 |
| Rust + TypeScript(Tauri) | 8~50MB | 70~180MB | 보통(Rust·TS·IPC 세 경계) | 둘 다 중간 — 메모리·초점 제어가 약점 |
| TypeScript만(Electron) | 90~350MB | 120~300MB | 화면은 쉬움, 핵심은 네이티브 부품 필요 | 둘 다 꼴찌 — 메모리 초과 확실 |

- GPT는 1판 C# → 2판 C++20 + Qt Widgets로 바꿨다. 이유: 메모리 80MB와 Windows 10 1903을 엄격한 조건으로 보면 네이티브가 유리. 스스로 「메모리를 120~150MB로 풀면 1등은 C#」이라고 적음. Qt는 지금 PasteFlow의 화면 도구와 같은 계열이다.
- 갈림의 열쇠: **메모리 80MB가 지금도 진짜 조건인가**(3월 PRD 목표) · 지금 앱의 실제 메모리(미실측).

### 메모리 예산과 지금 앱 실측 (2026-11-16)

- 사용자 답: **메모리 80MB는 풀어도 된다(120~150MB까지 괜찮음).** → GPT 2판의 조건부 1등(C#)과 Claude 2판 1등(C#)이 같아진다.
- 지금 앱 실측(이 PC, `dist/PasteFlow-1.49.0.exe`, 히스토리가 빈 첫 실행, 사용자 동의 뒤 32초 띄움): 프로세스 2개(단일 exe 풀기용 8MB + 앱 115MB). **작업 집합 합계 약 123MB · 개인 메모리 약 57MB.** 실행 2초 뒤 앱 프로세스가 뜨고 6초 무렵 메모리가 멈춤(2초 간격으로 재서 시작 시간은 대략값 — PRD 3초 예산보다 길 가능성, 추정). 평소처럼 히스토리가 쌓이면 더 클 것(추정).
- 그러니 지금 파이썬 앱도 이미 80MB를 넘고 「풀어 준」 범위 안에 있다. C#의 추정(40~100MB)과 차이는 크지 않을 수 있다 — **C#으로 바꾸는 가장 큰 이유는 메모리가 아니라 컴파일러 검사와 구조**가 된다.
- 측정 뒤 테스트가 만든 `%LOCALAPPDATA%\PasteFlow`와 임시 풀기 폴더를 지웠고, 자동 시작 등록은 바뀌지 않았다.

읽는 법:
- **지금 앱만 전체 기능**이라 메모리를 그대로 견주면 시험판에 유리하다. 시험판끼리(C# 대 Tauri)는 같은 기능이라 공정하다.
- Tauri는 exe가 가장 작지만 화면용 WebView2가 프로세스 6개를 더 띄워 메모리가 가장 크다. 작업 집합 합계는 프로세스끼리 같이 쓰는 메모리가 여러 번 들어가 부풀려진다(추정) — 개인 메모리 153MB가 더 믿을 만하다. 사용자가 풀어 준 예산(120~150MB)을 시험판 단계에서 이미 넘는다.
- C# 단일 파일 165MiB는 WPF와 WinForms 런타임을 통째로 담은 크기다(압축 옵션은 안 켬). PC에 .NET 데스크톱 런타임을 한 번 깔면 0.2MiB.
- 시작 시간은 재는 때마다 2배쯤 흔들렸다(C# 단일 851 → 478ms). 대략값이다. 지금 앱 3000ms는 메모리가 멈춘 시각으로 잰 대리값.
- 두 시험판 모두 「Ctrl+Shift+V를 삼키고 Ctrl+V 주입」이 메모장 대신 시험용 글상자 창에서 3번 다 순서대로 붙었고, 복사 때 뜨는 작은 창이 초점을 빼앗지 않았다(Tauri는 창 설정 `focus: false`만으로 됨). 워드·한글·노션·입력기 전환 팝업은 재지 않았다(사용자가 「자동만」을 고름).
- 지금 앱과 다른 점 하나: 시험판은 자기가 넣은 키를 `LLKHF_INJECTED`가 아니라 고유 표식(`dwExtraInfo`)으로 거른다. 자동 시험의 주입 키를 받아야 해서 바꿨다 — 사람 키에는 동작이 같다.
