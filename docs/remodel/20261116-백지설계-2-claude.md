## 1. 언어

**고를 것: C# (.NET 8, 이후 9) + Native AOT 또는 self-contained 단일 파일 게시.** 이유는 세 가지입니다. 이 도구는 대부분이 Windows API 호출입니다. 전역 키 후킹(`SetWindowsHookEx WH_KEYBOARD_LL`), 클립보드 형식 열거, UI Automation, Windows.Graphics.Capture, WASAPI가 그렇습니다. C#은 이 API들을 공식 래퍼(CsWin32, Windows App SDK 투영)로 직접 부릅니다. 그리고 AI가 C#과 WPF/WinUI 코드를 가장 많이 학습했고 컴파일러가 타입 오류를 먼저 잡아 줍니다. 마지막으로 화면과 OS 코드를 한 언어에서 다루므로 경계(IPC)에서 생기는 버그가 없습니다.

| 후보 | 실행 파일/설치 크기(추정) | 쉴 때 메모리(추정) | OS 깊은 곳 접근 | AI가 쓰고 고치기 | 화면 자주 바꾸기 | 가장 큰 약점 |
|---|---|---|---|---|---|---|
| C# (.NET 8, WPF) | 단일 파일 self-contained 약 70~150MB, 프레임워크 의존형은 약 5MB | 40~70MB | 매우 좋음 (CsWin32, UIA 내장, WinRT 직접) | 매우 좋음 (학습량 많고 타입 검사 강함) | 좋음 (XAML 핫리로드, 다만 문법이 낯섦) | 런타임 크기, 80MB 예산이 빠듯함 |
| Rust + Tauri (화면은 TypeScript) | 약 8~15MB | 웹뷰 프로세스 포함 80~150MB | 좋음 (windows crate), 단 비동기·수명 문법에서 AI가 자주 막힘 | 보통 (빌드 오류 반복 잦음, 두 언어를 오가야 함) | 매우 좋음 (웹 화면) | WebView2 메모리 때문에 80MB 예산 초과 위험, 초점 안 뺏는 창이 까다로움 |
| TypeScript만 (Electron) | 약 90~150MB | 120~250MB | 약함 (전역 키·클립보드 형식·UIA는 네이티브 애드온 필요) | 좋음 (단 네이티브 애드온 빌드가 취약) | 매우 좋음 | 메모리 예산 확실히 초과, 핵심 기능이 애드온에 의존 |
| C++ (Win32/Qt 없이 순수) | 약 1~5MB | 10~30MB | 최상 (직접) | 낮음 (메모리 안전 오류, 화면 코드 장황) | 낮음 | 사람이 못 읽는 코드에서 AI 실수가 크래시로 이어짐 |
| Rust (순수, egui/Slint) | 약 5~15MB | 30~60MB | 좋음 | 보통 | 보통 (도구가 덜 성숙, 한글 입력·IME 약함) | 한글 IME 처리와 투명 오버레이 완성도 |

**2등: Rust(순수) 또는 Tauri.** 무엇이 바뀌면 2등이 낫나: 메모리 80MB 한도가 절대 조건이 되고 화면이 단순해지면 Rust 순수 쪽입니다. 화면 꾸미기가 기능보다 중요해지고 메모리 한도를 풀면 Tauri입니다.

주의: C# 단일 파일의 크기가 부담이면 Native AOT로 약 20~40MB까지 줄일 수 있지만, WPF는 AOT를 지원하지 않습니다(추정, 확인 필요). 그래서 WPF 자체 게시 단일 파일로 가고 크기는 받아들입니다.

## 2. 화면 도구

**고를 것: WPF (.NET 8) + MVVM(CommunityToolkit.Mvvm), 오버레이와 주석 편집기는 WPF 안의 Canvas/`DrawingVisual` 직접 그리기.** 이유는 다음과 같습니다.

- 초점을 빼앗지 않는 패널은 `WS_EX_NOACTIVATE` 확장 스타일과 `ShowActivated=false`로 해결됩니다. WPF는 `HwndSource` 훅으로 이 스타일을 직접 줄 수 있어 가장 확실합니다.
- 전체 화면 투명 오버레이(캡처 영역 선택, 여러 모니터)는 `AllowsTransparency` 창과 모니터별 창 한 개씩으로 처리합니다. DPI는 `PerMonitorV2` 매니페스트로 맞춥니다.
- 주석 편집기는 `InkCanvas`와 도형 객체로 충분합니다.
- 화면 부품 재사용은 `ResourceDictionary` 스타일과 `UserControl` 단위로 합니다. 다크 테마·고대비는 리소스 사전 교체로 처리합니다.

**2등: WinUI 3.** 무엇이 바뀌면 2등이 낫나: 최신 Windows 룩(Mica, 둥근 모서리)이 꼭 필요하고 단일 파일 배포 제약을 버릴 수 있다면 WinUI 3입니다. 다만 비활성 창, 투명 전체 화면 창, 비패키지 배포에서 WinUI 3는 아직 까다롭습니다(추정). 3등은 WinForms인데, 오버레이와 고DPI 처리가 투박해 접었습니다.

## 3. 폴더 구조

**고를 것: 층별 프로젝트 3개 + 그 안에서 기능별 폴더.** 솔루션 하나를 세 프로젝트로 나눕니다.

- `Core` (순수 C#, Windows 비의존): 순차 붙여넣기 큐 상태 기계, 히스토리 규칙, 설정 모델, 단축키 충돌 검사. 시험이 가장 쉬운 층입니다.
- `Platform` (Windows 의존): 키보드 후크, 클립보드 읽기·쓰기, 캡처, 녹화, 마이크, UI Automation. 전부 `Core`가 정의한 인터페이스(`IClipboardGateway`, `IKeyInjector` 등)를 구현합니다.
- `App` (WPF): 화면, 뷰모델, 트레이. 기능 폴더(Panel, Capture, Memo, Settings, Ai)로 나눕니다.

큰 파일 막기: 한 파일 300줄 이하를 빌드 단계에서 검사하고(간단한 스크립트 또는 Roslyn 분석기 규칙), 넘으면 빌드를 실패시킵니다. 순차 붙여넣기 같은 핵심은 「키 입력 → 상태 기계 → 명령 목록」 형태로 만들어, 상태 기계는 부작용 없이 「무엇을 할지」만 돌려주고 실행은 Platform이 합니다. AI가 파일 하나만 보고 고치게 하려는 구조입니다.

**2등: 기능별 수직 분할(프로젝트 하나, 기능 폴더만).** 무엇이 바뀌면 2등이 낫나: 기능이 더 늘지 않고 시험 대상이 줄면 프로젝트 3개의 관리 비용이 아깝습니다. 단 이 도구는 OS 접촉부를 갈라 놓아야 시험이 가능하므로 저는 3층을 권합니다.

## 4. 데이터 저장

**고를 것: SQLite 한 파일(WAL 모드, `Microsoft.Data.Sqlite`) + 이미지·큰 형식 데이터는 파일로 분리.**

- 위치: `%LocalAppData%\앱이름\`. 안에 `app.db`, `blobs\` 폴더, `settings.json`.
- 히스토리·고정·메모는 SQLite 테이블에 둡니다(순서, 시간, 종류, 미리보기 글자, 고정 여부). 큰 본문(이미지, HTML, RTF, 앱 전용 형식 바이트)은 `blobs\해시값.bin`으로 두고 DB에는 경로와 해시만 둡니다. 같은 내용 중복도 해시로 막습니다.
- 비정상 종료 대비: SQLite WAL이 트랜잭션 단위로 지켜 주므로 복사 한 건마다 즉시 기록해도 충분히 빠릅니다. blob을 먼저 쓰고 DB 행을 나중에 쓰는 순서로, 고아 blob은 시작할 때 청소합니다.
- 설정은 사람이 열어 볼 수 있게 `settings.json`(버전 번호 포함). API 키는 `ProtectedData.Protect`(DPAPI, CurrentUser)로 암호화한 값을 따로 둡니다.
- 히스토리 한도(10~500개) 초과분은 DB와 blob을 함께 삭제합니다.

**2등: JSON 파일만.** 무엇이 바뀌면 2등이 낫나: 히스토리를 아예 재시작 뒤에 안 남기기로 하면 JSON이면 충분합니다. 하지만 지금은 크래시에도 안 잃어야 하므로 SQLite가 낫습니다.

## 5. 시험과 검사

**고를 것: 3단 구조.**

- **1단, 순수 로직 단위 시험(xUnit, 수백 건, 빌드마다):** `Core`의 순차 붙여넣기 상태 기계를 표 형태 시나리오(복사, 붙여넣기, 시간 경과, 평범한 Ctrl+V, 줄 소진)로 시험합니다. 시간은 `TimeProvider`를 가짜로 바꿔 10초 경과를 즉시 흉내 냅니다. 이 부분이 두 번 실패한 영역이므로 가장 두텁게 시험합니다.
- **2단, 정적 검사(빌드 실패 조건):** nullable 참조 켜고 경고를 오류로, Roslyn 분석기, `dotnet format --verify-no-changes`, 300줄 초과 검사, `Platform`이 `App`을 참조하지 못하게 하는 아키텍처 시험(NetArchTest).
- **3단, OS 접촉부 시험:** 가짜 `Platform`(인터페이스 구현체)으로 앱 전체 흐름을 시험하고, 진짜 OS 시험은 별도 「실기 시험」 묶음으로 둡니다. 진짜 후크는 시험용 메모장 프로세스에 `SendInput`으로 Ctrl+Shift+V를 쏘고 결과 텍스트를 읽는 시험을 밤에 수동으로 한 번 돌립니다(CI 불가, 데스크톱 세션 필요). 클립보드 형식 왕복(텍스트·PNG·HTML·RTF)은 시험 가능합니다. 화면은 WPF를 오프스크린으로 그려 스크린샷 비교(골든 이미지)를 몇 장만 둡니다.

핵심은 「키를 가로채는 짧은 구간」의 로그입니다. 후크 콜백 안에서는 아무것도 기다리지 않고 이벤트만 큐에 넣고 반환하며, 각 단계 시각을 로그에 남겨 100ms/50ms 예산 위반을 자동 감지하게 합니다.

**2등: 화면 자동화 시험(FlaUI) 위주.** 무엇이 바뀌면 2등이 낫나: 화면 회귀가 잦아져 사람 확인이 부담될 때 FlaUI로 핵심 화면 흐름을 추가할 만합니다.

## 6. 배포

**고를 것: GitHub Releases(비공개 저장소) + 자체 업데이트(Velopack).**

- 빌드: GitHub Actions `windows-latest`에서 `dotnet publish -r win-x64 --self-contained -p:PublishSingleFile=true`. 이어서 Velopack이 설치 파일(`Setup.exe`)과 델타 업데이트 파일을 만듭니다.
- 설치: PC마다 `Setup.exe` 한 번 실행(관리자 권한 불필요, 사용자 폴더 설치). 시작 프로그램 등록은 앱 설정에서 `HKCU\...\Run` 키로 합니다.
- 업데이트: 앱이 시작할 때 릴리스를 확인해 조용히 내려받고 다음 재시작에 적용합니다. 비공개 저장소는 읽기 전용 토큰이 필요한데 개인용이니 허용 범위입니다(DPAPI로 보관).
- 코드 서명은 없습니다(개인용). SmartScreen 경고는 처음 한 번 넘깁니다.

**2등: 공유 드라이브(구글 드라이브 폴더)에 zip을 올리고 PC마다 시작 때 새 버전을 복사하는 스크립트.** 무엇이 바뀌면 2등이 낫나: 외부 서비스나 토큰 관리가 싫고 PC가 3대 이하로 줄면 이 쪽이 단순합니다. 의존 도구가 하나 줄어드는 대신 롤백과 실패 처리를 직접 짜야 합니다.

## 가장 위험한 기술 지점 세 곳

**1. 전역 키 후킹 + 합성 입력(순차 붙여넣기의 심장).** 위험은 두 가지입니다. 저수준 후크 콜백이 느리면 Windows가 후크를 말없이 빼 버립니다(타임아웃, 기본 약 300ms 안팎, 확인 필요). 합성 Ctrl+V가 자기 후크에 다시 잡히는 되먹임도 있습니다.
- 다루는 법: 후크는 전용 스레드에서 메시지 루프를 돌리고, 콜백 안에서는 판정만 하고 즉시 반환합니다(클립보드 교체와 키 주입은 다른 스레드로). 도구가 주입한 키에는 `dwExtraInfo`에 표식을 달아 관찰에서 뺍니다. 한글 입력기 전환 팝업은 주입 사이에 더미 키(예: 무해한 가상키 0xE8)를 끼워 Ctrl+Shift 단독 입력 해석을 깨는 방식으로 막습니다(알려진 기법, 이 환경에서 실측 필요). 후크가 빠졌는지 주기적으로 감시해 다시 걸고 알림을 띄웁니다. 이 구간은 상태 기계 시험과 밤 실기 시험을 둘 다 겁니다.

**2. 클립보드 형식 왕복 복원과 자기 쓰기 구분.** 앱 전용 형식(노션 등), 지연 렌더링(delayed rendering) 형식, 큰 이미지는 읽는 순간 소유 앱이 아직 값을 주지 않거나 클립보드가 다른 프로그램에 잠겨(`CLIPBRD_E_CANT_OPEN`) 실패하기 쉽습니다. 도구가 쓴 것을 새 복사로 오인하는 문제도 있습니다.
- 다루는 법: `AddClipboardFormatListener`로 변경 알림을 받고, 열기 실패는 짧게 재시도(예: 10ms 간격 최대 몇 번)합니다. 형식은 이름과 바이트 전체를 원본 그대로 저장하고 되살릴 때 같은 순서로 씁니다. 자기 쓰기에는 사용자 정의 형식(예: `x-myhub-own`)을 하나 같이 얹어, 변경 알림에서 그 형식이 있으면 무시합니다. 모르는 형식 때문에 복원이 깨질 때를 대비해 「읽을 수 있는 형식만 저장하고 건너뛴 형식 이름을 로그에 남김」을 기본으로 하고, 앱별 시험 표본을 모아 갑니다.

**3. 다중 모니터·혼합 DPI에서의 캡처와 투명 오버레이, 그리고 화면 녹화.** 모니터마다 배율이 다르면 좌표가 틀어지고, 투명 전체 화면 창이 모니터를 가로지르는 선택에서 어긋나며, 장시간 MP4 녹화는 메모리와 인코더 안정성이 문제입니다. 다른 창의 부품 경계 알아내기(UI Automation)는 앱마다 느리거나 응답이 없을 수 있습니다.
- 다루는 법: 앱 전체를 `PerMonitorV2`로 선언하고 좌표를 전부 물리 픽셀 한 가지로 통일합니다(변환은 한 모듈에서만). 모니터마다 오버레이 창을 따로 둡니다. 캡처는 Windows.Graphics.Capture, 녹화는 프레임을 Media Foundation 인코더로 파일에 바로 흘려 씁니다(전체를 메모리에 모으지 않음). UI Automation 호출은 별도 스레드에서 시간 제한(예: 수십 ms)을 두고, 응답 없으면 창 단위 경계로 물러납니다. 다른 배율 두 대 모니터를 가진 PC에서 쓰는 실기 시험 목록을 만들어 두고 화면 바꿀 때마다 돌립니다.
