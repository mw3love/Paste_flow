## 결론

저라면 **C# + .NET 10 LTS + WPF**를 기본으로 선택하겠습니다. Windows API는 직접 호출하고, 데이터는 **SQLite와 파일 저장소**, 배포는 **Velopack 기반 사용자별 설치·업데이트**로 구성합니다.

이 선택의 중심은 “가장 가벼운 언어”가 아니라 **AI가 수정한 코드의 오류를 컴파일러·자동 시험으로 잡기 쉽고, Windows 기능과 화면을 한 사람이 계속 고칠 수 있는가**입니다.

다만, 아래 세 가지는 설계 전에 명확히 해야 합니다.

- **Ctrl+Shift+V를 그대로 보내면 모든 앱에서 붙여넣어진다는 보장은 없습니다.** 붙여넣기는 운영체제가 일괄 수행하는 것이 아니라 대상 앱이 단축키를 해석하고 클립보드를 읽는 동작입니다.
- **모든 앱 전용 클립보드 형식을 재시작 후까지 완벽하게 재현하는 것은 일반적으로 불가능합니다.** 다른 프로세스의 객체·스트림·임시 파일에 의존하는 형식이 있기 때문입니다.
- **상주 80MB와 복잡한 Windows 데스크톱 UI의 양립은 측정해야 합니다.** WPF로 충분하다고 미리 약속하지 않고, 실제 최소 구현을 합격 관문으로 삼겠습니다.

이 조건들을 숨기지 않고, 먼저 작은 기술 검증으로 확인한 뒤 나머지 기능을 쌓는 방식입니다.

## 1. 언어 — C# / .NET 10 LTS

### 고를 것

- **C# + .NET 10 LTS**
- Windows API 바인딩: **Microsoft.Windows.CsWin32**
- Windows COM·WinRT 연동: Windows 대상 TFM과 필요한 명시적 interop
- HTTP: **HttpClient**
- JSON: **System.Text.Json**
- 마이크: **NAudio의 WASAPI**
- 핵심 상태와 데이터 모델: nullable reference types를 켠 강한 타입

Windows 10 1903을 실제 최소 실행 대상으로 시험하되, **실행 가능 여부와 Microsoft의 공식 지원 여부는 별개**로 기록합니다. 오래된 Windows를 계속 지원한다면 보안·런타임 유지보수 비용을 받아들여야 합니다.

### 이유

1. **Windows API 접근성과 유지보수성의 균형이 좋습니다.**  
   클립보드, 저수준 키보드 훅, 창 스타일, UI Automation, DPAPI, 트레이를 모두 다룰 수 있습니다.

2. **AI가 만드는 코드에 안전장치를 걸기 쉽습니다.**  
   nullable 검사, 분석기, 명시적인 상태 모델, 자동 시험을 기본 빌드에 포함할 수 있습니다.

3. **화면과 업무 로직에 한 언어를 씁니다.**  
   개인용 도구에서 Rust/C++ 핵심부와 JavaScript UI를 함께 관리하는 비용을 피합니다.

4. **필요한 곳만 네이티브 경계로 격리할 수 있습니다.**  
   P/Invoke와 COM 코드를 앱 전체에 흩뜨리지 않고 작은 Windows 어댑터에 제한합니다.

### 실행 구조

처음부터 모든 기능을 별도 프로세스로 나누지는 않겠습니다.

- **본체:** 트레이, 클립보드, 단축키, 패널, 상태 관리
- **전용 스레드:** 키보드 훅, 클립보드/OLE STA 작업
- **필요할 때만 실행하는 작업 프로세스:** UI Automation 탐색, 녹화·인코딩 등 멈추거나 자원을 많이 쓸 수 있는 작업

전역 키 훅의 콜백에서는 **네트워크·디스크·SQLite·화면 갱신을 하지 않습니다.** 순차 붙여넣기의 다음 항목은 미리 준비해 둡니다.

### 2등과 역전 조건

**2등: C++20 + Qt 6**

상주 메모리 80MB가 어떠한 경우에도 넘으면 안 되는 절대 조건이고, 초기 측정에서 C#/WPF가 실패하면 이쪽이 유력합니다. Windows 네이티브 자원과 그래픽 파이프라인을 더 세밀하게 제어할 수 있습니다.

다만 비전공자가 AI로 유지보수한다는 조건에서는 메모리 수명, COM, 콜백, 스레드 문제의 비용이 큽니다. **실측 없이 메모리 우려만으로 C++부터 고르지는 않겠습니다.**

## 2. 화면 도구 — WPF, 캡처·녹화는 Windows 네이티브 API

### 고를 것

일반 화면은 **WPF + CommunityToolkit.Mvvm**로 만들겠습니다.

- 패널·설정창·메모창: WPF
- 재사용 부품: `UserControl`, `DataTemplate`, `ResourceDictionary`
- 목록: 가상화된 항목 목록, 지연 생성 썸네일
- 주석 편집기: WPF의 `DrawingVisual`·`DrawingContext` 기반 전용 캔버스
- 이미지 표시: WPF 이미지 표시와 별도 문서 좌표계
- 트레이: 작은 `Shell_NotifyIcon` 어댑터

큰 UI 프레임워크와 테마 패키지는 되도록 추가하지 않습니다. 색상·간격·글자 크기·선택 상태를 자체 디자인 토큰으로 관리합니다.

### 패널의 초점 처리

자동 표시와 사용자가 직접 연 경우를 **서로 다른 열기 동작**으로 정의합니다.

- 복사에 따른 자동 표시: `ShowActivated=false`, 비활성화 창 스타일, `SW_SHOWNOACTIVATE`
- Ctrl+Space로 열기: 명시적인 활성화 요청
- 메모창: 사용자가 입력하려고 연 창이므로 활성화
- 진행 상태 표시창·음성 음량 표시: 입력을 받지 않는 비활성화 오버레이

패널은 마지막 대상 창의 HWND를 보관합니다. 항목 클릭 시에는 대상 창 복원과 전경 전환이 확인된 뒤 붙여넣기를 요청합니다.

**이 클릭 붙여넣기는 핵심 순차 단축키와 별도 경로입니다.** 클릭 붙여넣기에서는 `SendInput`을 사용할 수 있지만, 순차 단축키에서는 이를 쓰지 않습니다. 전경 전환 실패나 관리자 권한 앱에 대한 입력 제한이 있으면 엉뚱한 창에 보내지 않고 알립니다.

### 주석 편집기

그림 위에 WPF 컨트롤을 수백 개 올리는 방식보다 다음 구조를 택합니다.

- 원본 이미지
- 도형·선·화살표·펜·글자·번호표의 **주석 문서 모델**
- 확대·이동을 위한 뷰 변환
- 명령 단위 실행 취소/다시 실행
- 저장할 때 원본과 주석을 합성

이렇게 하면 여러 미리보기 창, 확대 비율 변경, 저장 이미지 해상도를 서로 분리할 수 있습니다.

### 캡처·녹화 기반

| 기능 | 선택 |
|---|---|
| 화면 프레임 획득 | **Windows Graphics Capture**, 모니터별 캡처 |
| 그래픽 합성·잘라내기 | **D3D11** |
| 창 경계 | **DWM 확장 프레임 경계**, Win32 창 정보 |
| 버튼·편집 영역 경계 | **UI Automation** |
| MP4 녹화 | **Media Foundation H.264 인코더**, 스트리밍 파일 기록 |
| GIF 생성 | 임시 영상으로 기록한 뒤 **FFmpeg**로 변환 |

모니터를 가로지르는 선택은 모니터별 프레임을 가상 화면 좌표로 합성합니다. **Per-Monitor DPI Aware V2**를 적용하고 물리 픽셀과 WPF DIP 좌표 변환을 한 모듈에서 관리합니다.

UI Automation은 외부 앱 때문에 멈출 수 있으므로 **시간 제한이 있는 작업 프로세스**로 실행합니다. 실패하면 창 경계 스냅만 제공하고 자유 선택은 계속 동작하게 합니다.

MP4는 프레임을 메모리에 쌓지 않습니다. 비정상 종료 복구를 고려해 **fragmented MP4 또는 복구 가능한 구간 파일 기록**을 검증합니다. 디스크 부족·잠금 화면·장치 재설정도 정상적인 종료 사유로 처리합니다.

커서 포함 여부 등 OS 버전별 API 차이는 기능 감지로 분기합니다. 보호된 영상이나 보안 데스크톱은 캡처할 수 있다고 약속하지 않습니다.

### AI 기능의 화면 경계

AI 게이트웨이는 `Transcribe`, `RecognizeText`, `Translate`, `ListModels`, `TestConnection` 같은 인터페이스 뒤에 둡니다. 실제 HTTP 형식은 회사 API 문서에 맞춘 어댑터 하나가 담당합니다.

- API 호출은 비동기·취소 가능하게 구현
- 음성 입력은 시작 시 대상 창을 기억하되, 종료 시 대상이 바뀌면 무조건 붙이지 않음
- 이미지가 브라우저 검색으로 넘어가는 기능은 **지원되는 업로드 API나 공식 연결 방식**을 사용
- 지원 방식이 없다면 브라우저 열기와 이미지 복사·파일 준비까지만 자동화

임의의 웹페이지 DOM을 조작하는 자동화를 핵심 기능의 기반으로 삼지는 않겠습니다.

### 2등과 역전 조건

**2등: Qt 6 Widgets + 사용자 정의 그래픽 캔버스**

C++을 택하거나 메모리 제한이 최우선이면 더 적합합니다. 반대로 Windows 전용이고 화면을 자주 바꾸며 C#을 쓰는 조건에서는 WPF가 일관성이 좋습니다.

WinUI 3는 현대적인 외관이 최우선일 때 후보지만, 이 도구에서는 비활성화 창·작은 오버레이·트레이·네이티브 창 제어의 검증 부담을 더 중요하게 봅니다.

프로젝트를 수십 개로 쪼개거나 플러그인 구조를 미리 만들지는 않습니다.

### 순차 붙여넣기는 명시적인 상태 기계로

큐를 여러 이벤트 핸들러에서 직접 수정하지 않습니다.

예를 들어 다음 상태와 사건을 정의합니다.

- 상태: 비어 있음 / 수집 중 / 붙여넣기 진행 중 / 소진됨
- 사건: 외부 복사 / 순차 키 누름 / 일반 Ctrl+V / 목록으로 큐 지정
- 별도 값: 다음 인덱스, 마지막 외부 복사 시각, 이미지 경로 모드

핵심 규칙을 문서와 시험에 같이 적습니다.

- 10초가 지났다는 이유만으로 즉시 비우지 않고, **그 뒤 새 복사가 왔을 때** 새 큐를 시작
- 붙여넣기 시작 후 외부 복사가 오면 기존 큐를 대체
- 일반 Ctrl+V는 큐만 비우고 클립보드는 바꾸지 않음
- 자체 클립보드 기록은 외부 복사가 아님
- 패널에서 특정 항목 붙여넣기는 큐에 영향 없음
- 큐 소진 후에는 키를 관찰하더라도 클립보드를 바꾸지 않음

시계도 인터페이스로 주입해 10초 경계 시험에 실제 대기를 쓰지 않습니다.

### 큰 파일을 막는 방법

- 일반 소스 파일 **300줄 초과 경고, 500줄 초과 빌드 실패**
- 생성 코드·DB 마이그레이션은 명시적으로 예외
- 한 ViewModel에 녹화·클립보드·AI 처리를 몰아넣지 않기
- 분석기로 순환 의존과 금지된 프로젝트 참조 검사
- 공유 폴더에 업무 로직을 넣지 않기
- 대형 파일을 `partial`로 나누기만 하는 변경은 해결로 인정하지 않기

줄 수 제한보다 중요한 것은 **한 파일이 한 가지 변경 이유만 갖게 하는 것**입니다.

AI 코딩 지침에는 “행동 규칙을 바꾸면 해당 시험도 바꾼다”, “Windows 호출을 화면 코드에 추가하지 않는다”를 넣습니다.

### 2등과 역전 조건

**2등: 단순한 층별 구조 — UI / Services / Models / Infrastructure**

기능이 몇 개뿐인 작은 도구라면 더 간단합니다. 하지만 이 범위에서는 `Services`와 거대한 `MainViewModel`로 모이기 쉬워 기능별 구조가 낫습니다.

## 4. 데이터 저장 — SQLite + 원본 형식 파일 저장소

### 고를 것

사용자별 로컬 폴더 아래에 저장합니다.

```text
%LOCALAPPDATA%\PersonalHub/
  data/
    hub.db
    blobs/
    thumbnails/
  secrets/
    gateway-key.bin
  logs/
  recovery/
  temp/
```

- 구조화된 데이터: **SQLite + Microsoft.Data.Sqlite**
- DB 모드: **WAL**, `synchronous=FULL`
- 이미지·클립보드 원본 페이로드: 파일 저장소
- 설정: DB의 버전 있는 설정 테이블
- API 키: **DPAPI CurrentUser**
- 이미지 주석: 버전 있는 JSON 문서
- 로그: 크기·보관 기간 제한이 있는 순환 로그

PC 3~4대에 같은 프로그램을 설치하는 것과 데이터를 동기화하는 것은 별개입니다. **실행 중 SQLite DB를 OneDrive 폴더에 넣지 않습니다.** 설정은 명시적인 내보내기·가져오기로 옮기고 API 키는 PC마다 입력합니다.

### 클립보드 원본 보존

항목에는 표시용 데이터와 복원용 데이터를 따로 둡니다.

- 표시용: 제목, 두 줄 미리보기, 썸네일, 종류
- 복원용: 형식별 식별 정보와 원본 페이로드

텍스트만 뽑아서 저장하지 않고 다음을 함께 보존합니다.

- Unicode text
- HTML Format
- RTF
- DIB/DIBV5 등 이미지 표현
- 등록된 앱 전용 형식
- 처리 가능한 OLE 데이터

등록 형식은 재시작 후 숫자 ID가 달라질 수 있으므로 **등록 이름을 저장하고 다시 등록**합니다.

다만 모든 형식을 `GetClipboardData`의 메모리 블록으로 복사하면 되는 것은 아닙니다. GDI 핸들, `IStream`, 지연 렌더링, 가상 파일, 외부 파일 참조에는 별도 어댑터가 필요합니다.

따라서 형식마다 다음 상태를 기록합니다.

- 완전 복원 가능
- 일부 형식만 복원 가능
- 현재 세션에서만 사용 가능
- 지원하지 않음

**“원본 그대로 보존됐다”는 표시를 근거 없이 하지 않는 것**이 중요합니다.

### 비정상 종료 대응

저장 순서를 정합니다.

1. 원본을 임시 파일에 기록
2. 파일을 flush하고 최종 이름으로 이동
3. DB 트랜잭션으로 항목과 파일 참조를 커밋
4. 커밋 후 저장 완료 상태 표시

중간에 종료되면 참조되지 않는 파일이 남을 수 있지만, DB가 존재하지 않는 파일을 정상 항목으로 가리키는 상황은 피합니다. 시작할 때 정리·무결성 검사를 수행합니다.

“비정상 종료에도 히스토리를 잃지 않는다”는 **저장 완료된 항목에 대한 보장**으로 정의해야 합니다. 복사 직후 아직 읽거나 저장하지 못한 데이터, 하드웨어 고장까지 무손실로 보장할 수는 없습니다.

### 메모리·보관 정책

- 기본 히스토리 50개, 설정 범위 10~500
- 고정 항목과 일반 히스토리 보관 정책 분리
- 원본 이미지는 필요할 때만 읽기
- 썸네일은 별도 파일로 만들고 메모리 캐시에 상한 설정
- 다음 붙여넣기 항목만 선행 준비
- 항목 수 외에 디스크 사용량과 단일 항목 크기 경고 제공

이미지 경로 붙여넣기용 PNG는 별도 수명 정책을 갖습니다. 대상 AI 도구가 나중에 읽을 수 있으므로 붙여넣기 직후 삭제하지 않습니다.

메모 일괄 삭제는 즉시 물리 삭제하지 않고 **짧은 되돌리기 유예가 있는 휴지통 처리**로 구현합니다. 자동 저장은 짧게 지연 병합하되, 아직 저장되지 않은 상태를 구분합니다.

API 키는 로그·설정 내보내기·백업에 넣지 않습니다. DPAPI는 동일 사용자 권한의 악성 프로그램까지 막는 보안 경계는 아니라는 점도 전제합니다.

### 2등과 역전 조건

**2등: JSON 파일 + 이미지 폴더**

설정만 저장한다면 좋습니다. 하지만 히스토리, 고정 순서, 삭제 취소, 비정상 종료 복구가 있는 이 도구에서는 여러 JSON 파일의 일관성을 직접 관리하는 편이 더 어렵습니다.

## 5. 시험과 검사 — 순수 로직 시험과 실제 Windows 시험을 분리

### 고를 것

- 단위 시험: **xUnit**
- 상태 조합 시험: **FsCheck**
- 정적 검사: .NET 분석기, nullable 경고, 경고를 오류로 처리
- 형식 검사: **dotnet format --verify-no-changes**
- 구조 검사: **NetArchTest** 또는 동일 목적의 자체 검사
- UI 시험: **FlaUI / UIA3**
- 성능 분석: **ETW, Windows Performance Recorder, PerfView**
- 실행 환경: 전용 Windows VM과 실제 사용 PC

### ① 순수 로직 시험

순차 붙여넣기는 몇 가지 예제로 끝내지 않고 사건 조합을 생성해 검사합니다.

예:

```text
복사 A → 복사 B → 순차 키 → 복사 C → 순차 키
복사 A → 11초 경과 → 복사 B
복사 A → 순차 키 → 일반 Ctrl+V
복사 A → 패널에서 X 붙이기 → 순차 키
자체 클립보드 기록 → 클립보드 변경 알림
순차 키를 누른 채 유지 → 반복 keydown
```

다음 불변 조건을 검사합니다.

- 자체 기록으로 큐 길이가 늘지 않음
- 일반 붙여넣기 경로에서 키를 삼키지 않음
- 소진 후 클립보드를 다시 쓰지 않음
- 패널 개별 붙여넣기로 순차 인덱스가 바뀌지 않음
- 클립보드 교체 실패 시 항목을 소비하지 않음
- 재진입·중복 알림에도 상태가 깨지지 않음

단축키 길게 누르기는 기본적으로 **한 번의 물리적 누름당 한 항목**으로 정의하겠습니다.

### ② 클립보드 통합 시험

시험용 생산자 앱과 소비자 앱을 직접 만듭니다.

생산자 앱은 다음을 제공합니다.

- 텍스트·HTML·RTF·이미지·사용자 정의 형식
- 지연 렌더링
- 클립보드 잠금
- 데이터 제공 직후 종료
- 큰 이미지와 깨진 페이로드

소비자 앱은 다음 방식으로 클립보드를 읽습니다.

- 키다운 즉시
- 키업 때
- 메시지 처리 후 지연 읽기
- HTML 우선, 이미지 우선 등 형식별 읽기

이 시험으로 **우리가 보장할 수 없는 대상 앱 동작까지 드러내야 합니다.** 시험용 앱이 통과했다고 모든 Windows 앱이 통과한다고 간주하지 않습니다.

실제 사용하는 Notion, 브라우저, 터미널, 편집기 등은 별도 호환성 목록으로 유지합니다.

### ③ UI·Windows 동작 시험

- 자동 패널 표시 전후 전경 HWND와 포커스가 유지되는지
- Ctrl+Space에서만 활성화되는지
- 패널 클릭 후 다른 창으로 오입력하지 않는지
- 모니터 연결 해제 후 창이 화면 밖에 남지 않는지
- 100%·150%·200% 혼합 DPI
- 음수 좌표의 모니터, 세로 모니터
- UI Automation 대상 앱 정지
- 마이크 분리·권한 거절
- 녹화 중 디스크 부족·절전·장치 재설정
- 관리자 권한 대상 창

이 시험은 **로그인된 대화형 데스크톱**에서 실행합니다. 일반적인 백그라운드 CI 서비스만으로 실제 초점·키보드 동작을 검증할 수는 없습니다.

### ④ 충돌·복구 시험

프로세스를 임의 시점에 강제 종료하는 시험을 만듭니다.

- 원본 파일 저장 중
- DB 커밋 전후
- 메모 자동 저장 중
- GIF 변환 중
- MP4 녹화 중
- 업데이트 준비 중

재시작 시 DB 무결성, 파일 참조, 고정 순서, 복구 가능 녹화를 검사합니다.

### ⑤ 성능 합격 관문

요구 수치를 측정 가능한 문장으로 바꿉니다.

| 항목 | 측정 방식 |
|---|---|
| 복사 감지 100ms 미만 | 변경 발생부터 앱이 사건을 수신하기까지 |
| 교체 50ms 미만 | 순차 keydown 관찰부터 클립보드 교체 완료까지 |
| 상주 메모리 80MB 미만 | 본체와 남아 있는 작업 프로세스 합계, 안정 상태에서 측정 |
| 유휴 CPU 0.5% 미만 | 정해진 기준 PC에서 충분한 시간 평균 |
| 트레이 표시 3초 미만 | 콜드 시작과 웜 시작을 분리 |

작업 집합과 private bytes를 모두 보고하고, 메모리를 강제로 비워 숫자만 낮추지 않습니다. 평균뿐 아니라 p95·p99·실패율도 남깁니다.

큰 이미지의 완전 복제나 클립보드 잠금까지 포함한 **모든 경우의 50ms 보장**은 별도 문제입니다. 정상 크기 범위와 예외 동작을 합의해야 합니다.

### 2등과 역전 조건

**2등: 단위 시험 + 수동 체크리스트**

초기 기술 검증 단계에서는 충분할 수 있습니다. 그러나 매일 쓰는 클립보드 도구이고 AI가 반복 수정한다면, 실제 Windows 통합 시험 없이 장기 운영하는 것은 추천하지 않습니다.

## 6. 배포 — Velopack, 단일 설치 파일, 사용자별 자동 업데이트

### 고를 것

- 빌드: 고정된 .NET SDK와 잠긴 NuGet 의존성
- 게시: **self-contained win-x64**
- 설치·업데이트: **Velopack**
- 배포물: 사용자는 **Setup.exe 하나**를 받아 실행
- 설치 위치: 사용자별 `%LOCALAPPDATA%`
- 업데이트 원본: 인증된 HTTPS 배포 위치 또는 접근 통제된 사내 배포 서버

실제로 ARM64 PC를 사용한다면 별도 빌드를 추가합니다. 처음부터 사용하지 않는 아키텍처까지 관리하지 않습니다.

### 단일 실행 파일보다는 단일 설치 파일

WPF, 런타임, 작업 프로세스, 인코딩 도구까지 억지로 하나의 실행 파일에 압축하지 않겠습니다.

**사용자 경험은 파일 하나, 내부 설치는 여러 파일**로 두는 편이 시작 시간, 진단, 업데이트에 유리합니다. WPF에 맞지 않는 Native AOT나 공격적인 trimming을 기본 전제로 하지 않습니다.

### 업데이트 규칙

- 시작 직후 트레이를 먼저 표시하고 업데이트 확인은 나중에
- 녹화·받아쓰기·붙여넣기 처리 중 자동 재시작 금지
- 다운로드 후 사용자가 정한 안전한 시점에 교체
- 프로그램 파일과 사용자 데이터 분리
- DB 마이그레이션 전 백업
- 이전 버전으로 돌아갈 수 있는 앱 패키지 보관
- DB 변경은 가능한 한 추가형으로 하고, 파괴적 변경은 별도 절차 적용

업데이트 파일은 해시만 확인하는 것으로 끝내지 않습니다. **서명된 배포 정보 또는 서명된 실행 파일의 신뢰 확인**을 포함합니다. 가능하면 코드 서명을 적용합니다.

FFmpeg를 함께 넣는다면 사용하는 빌드의 라이선스와 코덱 구성을 고정하고 기록합니다.

### 시작 프로그램과 단축키

- 자동 실행: 사용자별 `HKCU\...\Run` 등록·해제
- 일반 기능 단축키: `RegisterHotKey`로 충돌 확인
- 순차 붙여넣기와 일반 Ctrl+V 관찰: 저수준 키보드 훅

다른 프로그램이 자체 훅으로 처리하는 단축키까지 **완전하게 충돌 감지할 수는 없습니다.** 등록 가능한 충돌과 예약 조합은 검사하고, 나머지는 설정창의 실제 동작 시험으로 확인합니다.

### 2등과 역전 조건

**2등: self-contained ZIP + 수동 교체**

처음 기술 검증을 배포할 때는 가장 간단합니다. 하지만 PC 3~4대에서 자주 수정한다면 버전 불일치와 덮어쓰기 실수가 생겨 설치·업데이트 도구의 이점이 커집니다.

MSIX는 조직 차원의 서명·배포 체계가 이미 있을 때 다시 검토하겠습니다.

# 가장 위험한 기술 지점 세 곳

## 1. 키를 통과시키면서 정확한 시점에 클립보드를 바꾸는 일

**가장 먼저 검증할 지점입니다.**

선택하는 구현은 `WH_KEYBOARD_LL`에서 순차 단축키의 keydown을 관찰하고, 미리 준비한 항목으로 클립보드를 교체한 뒤 **항상 다음 훅으로 전달**하는 방식입니다.

- `RegisterHotKey`로 핵심 단축키를 소비하지 않음
- 원래 키를 막고 나중에 `SendInput`으로 재생하지 않음
- 일반 Ctrl+V도 그대로 전달
- 클립보드 잠금 시 길게 기다리지 않음
- 실패하면 큐 인덱스를 유지하고 오류를 알림

다만 **교체 완료 후 키를 넘기려면 그 짧은 시간만큼 키 전달이 늦어집니다.** “키를 삼키지 않는다”는 조건은 만족시킬 수 있지만, “전달을 전혀 지연하지 않으면서 교체가 반드시 먼저 끝난다”는 보장은 할 수 없습니다.

또한 키를 넘긴 뒤 다른 프로그램이 클립보드를 바꾸거나, 대상 앱이 Ctrl+Shift+V를 붙여넣기로 해석하지 않는 경우까지 해결할 수는 없습니다.

**대응:** 다른 기능보다 먼저 실제 사용 앱으로 검증합니다. 지원 대상 앱과 실패 시 동작을 문서화하고, 맞지 않으면 요구를 조정합니다. 우회 입력을 몰래 넣어 요구를 만족한 것처럼 만들지 않습니다.

## 2. 앱 전용 형식 보존과 자체 기록 판별

HTML만 남고 Notion 전용 데이터가 사라지거나, 자체 기록이 새 복사로 들어오면 핵심 기능이 무너집니다.

**대응:**

- 원본 형식을 종류별로 보존하는 어댑터 구성
- 자체 기록에는 비공개 등록 형식의 출처 표식 추가
- 출처 표식 하나만 믿지 않고 클립보드 sequence number, 기록 세대, 예상 내용과 함께 판별
- 지연 렌더링과 재진입을 통합 시험
- 복원이 불완전한 항목은 명시적으로 표시
- 실제 사용하는 앱의 형식 왕복 시험을 회귀 시험으로 유지

특히 `CF_HDROP`처럼 파일 경로만 가진 데이터는 “클립보드 저장”과 “참조 파일 보존”을 구분해야 합니다.

## 3. 다른 앱·장치·다중 모니터를 건드리는 캡처와 녹화

UI Automation 정지, 혼합 DPI, 녹화 인코더 지연, 마이크 장치 해제는 모두 실제 사용 중 자주 만날 수 있는 경계입니다. 한 기능의 실패가 클립보드 허브 전체를 멈추면 안 됩니다.

**대응:**

- 위험한 탐색·인코딩 작업을 필요 시 별도 프로세스로 격리
