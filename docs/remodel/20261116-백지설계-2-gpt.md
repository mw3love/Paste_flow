## 결론

저라면 **C++20 + Qt Widgets + Windows 네이티브 API**로 만듭니다. 저장은 **SQLite + 별도 원본 데이터 파일**, 배포는 **사용자 계정에 설치되는 단일 EXE 설치 파일**을 고르겠습니다.

이 선택의 결정적인 이유는 다음 두 가지입니다.

- **상주 메모리 80MB와 Windows 10 1903을 실제 제약으로 취급**하면, 네이티브 구성이 유리합니다.
- 이 도구의 어려운 부분은 화면보다 **키 입력·클립보드 원본 형식·캡처·녹화 등 Windows 경계**에 있습니다.

다만 **AI가 코드를 안전하게 고치기 쉬운 언어는 C#이 더 낫습니다.** 따라서 메모리 예산을 120~150MB 정도로 완화하고 지원 OS를 현재 지원되는 Windows 버전으로 좁힐 수 있다면, 제 1순위는 **C# + WPF**로 바뀝니다.

또한 아래 세 가지는 구현 언어와 관계없이 구분해야 합니다.

1. 다른 프로그램이 클립보드를 오래 잠그면 **50ms 교체를 절대 보장할 수는 없습니다.**
2. 앱 전용 형식 중에는 **다른 프로세스나 재시작 뒤에 복원할 수 없는 형식**이 있습니다.
3. Windows 10 1903에서 실행되는 것과, OS·개발 도구 공급사가 그 환경을 현재 공식 지원하는 것은 다릅니다.

이 한계를 숨기지 않고, 정상 경로의 성능 기준과 예외 동작을 먼저 정하겠습니다.

# 1. 언어

## 후보 비교

아래 수치는 **동일한 기능 범위의 제품을 만들었을 때 예상하는 대략적인 범위**입니다. 실측값이 아닙니다.

- 크기는 압축 설치 파일이 아니라 **설치 후 앱·필수 런타임이 차지하는 용량** 기준입니다.
- 메모리는 화면을 닫고 트레이에서 대기하는 상태의 **관련 프로세스 전체 작업 집합 합계**입니다.
- 원본 이미지·히스토리 파일, 로컬 AI 모델은 제외합니다.
- 런타임 공유 여부, 디버그 정보, 이미지 캐시 등에 따라 크게 달라집니다.

| 후보 | 예상 설치 용량 | 쉴 때 상주 메모리 | Windows 깊은 곳 접근 | AI가 작성·수정하기 쉬움 | 화면 변경 | 이 도구에서 가장 큰 약점 |
|---|---:|---:|---|---|---|---|
| **C# + WPF** | 자체 포함 배포 약 **80~160MB**. .NET이 이미 있다면 앱 자체는 훨씬 작음 | 약 **45~100MB** | 매우 좋음. P/Invoke·COM·WinRT 필요 | **가장 유리한 편**. 타입 검사, 관리형 메모리, 테스트 생태계 | 좋음. XAML·스타일·사용자 컨트롤 | 80MB를 안정적으로 지키기 까다롭고, 1903에서 최신 .NET의 공식 지원을 전제할 수 없음 |
| **Rust + TypeScript / Tauri** | WebView2가 이미 있으면 약 **15~50MB**. 고정 런타임 포함 시 **150~300MB 이상** 가능 | 약 **70~180MB** | 좋음. `windows` 크레이트로 접근하지만 COM·콜백·핸들 경계는 어려움 | Rust 자체의 검사는 강력함. 다만 Rust·TS·IPC 세 경계를 AI가 함께 다뤄야 함 | **매우 좋음** | WebView2 메모리와 구형 OS 대응, 네이티브 오버레이·키보드와 웹 UI 사이 복잡성 |
| **TypeScript만 / Electron** | 약 **180~350MB** | 약 **140~300MB** | TS만으로는 부족. 결국 네이티브 모듈이나 별도 프로그램 필요 | 일반 UI는 쉬움. 네이티브 모듈이 들어가면 난도 상승 | **매우 좋음** | 메모리 요구와 맞지 않으며, 엄밀한 의미의 “TypeScript만”으로 핵심 기능을 구현하기 어려움 |
| **C++20 + Qt Widgets** | 약 **30~90MB** | 약 **20~60MB** | **가장 직접적**. Win32·COM·D3D11·Media Foundation 사용 | 상대적으로 불리함. 수명·스레드·포인터 실수를 자동 검사로 보완해야 함 | 좋음. 재사용 위젯·모델/뷰 구성 필요 | AI가 만든 메모리·동시성 오류가 컴파일을 통과할 수 있음 |

Tauri에서 WebView를 완전히 없애고 필요할 때만 다시 만들면 대기 메모리를 줄일 수 있습니다. 하지만 패널의 첫 표시 지연과 상태 복구가 추가되어, 이 도구에는 별도 부담입니다.

## 선택: C++20

구체적으로 다음을 고릅니다.

- **MSVC**
- **C++20**
- **CMake + Ninja**
- **vcpkg manifest와 baseline 고정**
- **Qt 6 Widgets**
- COM·핸들 관리: **Microsoft WIL**, `ComPtr`, 자체 소형 RAII 래퍼
- 정적 검사: **clang-tidy, MSVC `/analyze`**
- 메모리 검사: **AddressSanitizer**

Qt 버전은 **Qt 6.8 계열을 최초 호환성 검증 후보**로 잡겠습니다. 실제 채택 패치 버전과 도구 체인은 Windows 10 1903에서 검증한 뒤 고정합니다. 이후 Qt를 올릴 때도 최소 OS 시험을 통과해야 합니다.

C++를 선택한다고 해서 앱 전체를 Windows 메시지와 포인터로 작성하지는 않습니다.

> Windows와 맞닿는 부분만 작은 네이티브 어댑터로 만들고, 순차 붙여넣기 규칙·히스토리 정책·설정은 운영체제와 분리된 일반 C++ 코드로 작성합니다.

**2등: C# + WPF**

메모리·최소 OS 제약을 완화할 수 있다면 C#이 더 적합합니다. 한 명의 비전공자가 AI를 통해 유지보수한다는 조건에서는, 관리형 메모리와 컴파일러가 제공하는 보호가 큰 장점입니다.

| 설정창 | Qt Widgets, 공통 설정 행 컴포넌트 | 단축키·모델·장치·색상 설정을 재사용하기 쉬움 |

Qt Quick/QML은 화면을 꾸미기 쉽지만, 이 도구에서는 **메모리·비활성 창·복잡한 창 간 입력 동작을 단순화하는 것**을 우선합니다.

## 초점 정책은 화면 코드에 흩어 놓지 않습니다

`FocusCoordinator`를 두고 다음 두 경로를 명시적으로 나눕니다.

- **복사로 자동 표시:** `WS_EX_NOACTIVATE`, `SW_SHOWNOACTIVATE` 등을 사용해 초점을 가져오지 않음.
- **Ctrl+Space로 직접 표시:** 사용자 요청으로 활성화하고 검색·선택 가능.

패널을 열기 전의 대상 창을 기억합니다. 항목 클릭 시에는 다음 순서로 처리합니다.

1. 붙여넣을 데이터를 준비.
2. 패널을 닫거나 비활성화.
3. 대상 창이 여전히 유효한지 확인.
4. 대상 창으로 초점 복귀를 요청하고 실제 전경 창을 확인.
5. 확인된 경우에만 붙여넣기.

복귀에 실패하면 **엉뚱한 창에 입력하지 않고, 복사만 해 둔 뒤 알립니다.** `SetForegroundWindow`가 항상 성공한다고 가정하지 않습니다.

## 기능별 네이티브 기술

### 캡처와 선택

- 픽셀 획득: **DXGI Desktop Duplication + D3D11**
- 차선책: **Windows Graphics Capture**
- 창 경계: `EnumWindows`, `GetWindowRect`, `DwmGetWindowAttribute`
- 창 내부 부품: **UI Automation**
- DPI: **Per-Monitor DPI Awareness V2**

1903부터의 일관된 모니터 캡처·커서 합성을 위해 Desktop Duplication을 먼저 택합니다. Windows Graphics Capture는 실제 대상 환경에서 더 안정적이면 교체할 수 있도록 인터페이스 뒤에 둡니다.

여러 모니터를 가로지르는 선택은 **가상 데스크톱의 물리 픽셀 좌표**로 저장합니다. 각 모니터 프레임을 합성하므로 모니터 간 완전한 동시 프레임은 보장하지 않습니다.

UI Automation은 다른 앱 때문에 느려지거나 멈출 수 있습니다. 따라서:

- 마우스 이동 이벤트에서 동기 호출하지 않음.
- 별도 작업자에서 조회하고 결과 캐시.
- 응답이 늦으면 창 경계나 자유 선택으로 즉시 대체.
- 내부 부품을 노출하지 않는 앱에서는 부품 자석 기능이 제한됨.

### 녹화

- MP4: **D3D11 + Media Foundation**, 가능하면 하드웨어 H.264 인코더.
- 긴 녹화: 메모리에 전체 프레임을 모으지 않고 **유한 길이 버퍼에서 바로 파일로 기록**.
- 비정상 종료 피해 축소: **fragmented MP4**를 우선 검증.
- GIF: **giflib**, 낮춘 프레임률·크기, 프레임 단위 기록.

“길이 제한 없음”은 앱의 인위적 제한이 없다는 뜻으로 정의합니다. 디스크 부족·파일 시스템 한계·장치 오류는 감지하고 알립니다. 인코더가 밀리면 메모리를 무한히 늘리지 않고 정해 둔 정책으로 프레임을 버립니다.

### 주석

도형·선·화살표·펜·글자·번호표를 각각 독립된 편집 항목으로 만듭니다. **원본 이미지와 주석 모델을 분리**하고, 내보낼 때 합성합니다.

여러 미리보기 창이 동일 원본을 참조할 수 있지만, 편집 상태는 창별 문서로 관리합니다.

### 음성·AI·브라우저

- 마이크: **WASAPI**, 장치 열거는 `IMMDeviceEnumerator`.
- 음량: 오디오 콜백에서는 수치만 계산하고, UI 갱신은 제한된 빈도로 수행.
- 웹 API: **Qt Network `QNetworkAccessManager`**.
- 회사 게이트웨이: OCR·번역·음성 인식·모델 조회를 각각 어댑터로 분리.
- “연결 시험”: 통신·인증뿐 아니라 선택한 모델의 해당 기능 지원까지 확인.

사내 게이트웨이가 OpenAI와 같은 규격이라고 가정하지 않습니다.

브라우저 AI 검색에 이미지를 보내는 기능도 **서비스가 제공하는 업로드 방식이 있는지 먼저 확인**합니다. 단순 URL 열기만으로 로컬 이미지를 첨부할 수 있다고 가정하지 않습니다. 지원되는 연동이 없다면 이미지 복사와 브라우저 열기까지 자동화하고, 마지막 붙여넣기는 사용자에게 맡기는 경로를 제공합니다.

**화면 도구 2등:** C#을 택한다면 WPF. 화면 변경의 편의성이 메모리보다 중요해지면 이 조합이 낫습니다.


실제 문서와 코드 설명은 한국어로 작성하되, 식별자는 일관된 영어를 사용하겠습니다.

## 가장 중요한 분리

다음 네 가지는 다른 객체로 둡니다.

- **히스토리:** 복사한 기록.
- **순차 줄:** 이번에 붙여넣을 항목 ID의 순서와 위치.
- **시스템 클립보드:** 현재 Windows에 올라간 데이터.
- **붙여넣기 실행기:** 대상 창과 키 상태를 확인하고 입력을 전달.

이들을 하나의 `ClipboardManager`에 합치지 않습니다. 그래야 “패널에서 하나 붙이기”가 순차 줄을 바꾸는 오류를 구조적으로 막을 수 있습니다.

순차 줄은 명시적인 상태 기계로 만듭니다.

- 수집 중 새 복사: 마지막 복사와의 간격에 따라 추가 또는 새 줄.
- 순차 붙여넣기를 시작한 뒤 새 복사: 기존 줄을 비우고 새 줄.
- 일반 Ctrl+V 관찰: 줄 비우기.
- 도구가 넣은 Ctrl+V: 무시.
- 패널 붙여넣기: 줄 변경 없음.
- 여러 항목으로 줄 지정: 명시적인 별도 명령.

시간은 테스트 가능한 단조 시계 인터페이스로 받습니다.

## 큰 파일 방지

- 일반 소스 파일 **300줄부터 경고, 500줄 초과는 사유가 없으면 CI 실패**.
- 생성 코드·마이그레이션은 예외.
- 함수 복잡도·순환 의존성 검사.
- 도메인 타깃에는 Windows 헤더와 Qt Widgets 의존 금지.
- 예외 없는 “공용 유틸 모음” 확장 금지.
- AI에 주는 변경 단위는 “한 기능 + 그 시험 + 계약 문서”로 제한.

파일을 작게 만드는 것보다 **의존 관계를 작게 만드는 것**이 더 중요합니다.

**2등:** 전체를 UI·서비스·저장소 같은 층별 폴더로만 나누는 방식. 기능이 아주 적을 때는 단순하지만, 이 정도 기능 수에서는 한 수정이 여러 거대 폴더에 흩어집니다.

# 4. 데이터 저장

## 선택: SQLite + 불변 원본 파일

위치는 기본적으로 다음과 같습니다.

```text
%LOCALAPPDATA%\PersonalHub/
  data/
    hub.db
    blobs/
    thumbnails/
  settings/
    settings.json
  secrets/
    gateway-key.dpapi
  exports/
  logs/
```

데이터베이스와 원본 파일을 OneDrive 같은 동기화 폴더에 직접 두지 않습니다. **3~4대에 앱을 배포하는 문제와 클립보드 내용을 동기화하는 문제는 분리**합니다. 후자는 현재 요구가 아닙니다.

| 데이터 | 저장 방식 |
|---|---|
| 히스토리·고정·메모·순차 줄 메타데이터 | SQLite |
| 고정 순서 | DB의 정렬 키, 드래그 완료 시 트랜잭션 |
| 클립보드 원본 형식 | 형식 목록 + 형식별 불변 파일 |
| 원본 이미지 | 받은 형식 보존, 필요 시 별도 PNG 생성 |
| 썸네일 | 재생성 가능한 디스크 캐시 |
| 설정 | 스키마 버전이 있는 JSON, 임시 파일 후 원자적 교체 |
| API 키 | `CryptProtectData`, 사용자 범위 DPAPI, 로컬 파일 ACL |
| 영상·GIF | 사용자가 고른 출력 폴더 |

API 키 파일은 PC 간 복사하지 않고 각 PC에서 다시 입력합니다. DPAPI는 다른 계정·오프라인 탈취에 대한 보호 수단이지, 같은 사용자 권한으로 실행되는 악성 코드로부터의 완전한 보호는 아닙니다.

## 클립보드는 “문자열 또는 이미지”로 저장하지 않습니다

한 항목은 예를 들어 다음 형식을 동시에 가질 수 있습니다.

- `CF_UNICODETEXT`
- HTML Format
- Rich Text Format
- DIB/DIBV5
- PNG 등록 형식
- 앱 전용 등록 형식
- OLE 데이터 형식

등록 형식은 숫자 ID만 저장하지 않고 **형식 이름**을 저장합니다. 다시 올릴 때 등록해서 현재 세션의 ID를 얻습니다.

클립보드 작업은 전용 STA 경계에서 수행하고, 형식의 실제 데이터를 읽어 보관합니다. 알려진 핸들 기반 형식은 복사·직렬화 규칙을 별도로 구현합니다.

다만 다음은 분명히 구분합니다.

> 알 수 없는 모든 형식을 바이트로 복사하면 원래대로 살아나는 것은 아닙니다.

프로세스 내부 포인터·실시간 COM 객체·나중에 제공되는 가상 파일 등이 포함된 형식은 일반적인 영구 복원이 불가능할 수 있습니다.

따라서 노션 등 실제 사용하는 앱을 호환성 목록에 넣고:

- 어떤 형식이 제공되는지.
- 어떤 형식을 보존해야 원하는 붙여넣기가 되는지.
- 원본 앱을 닫거나 재시작해도 복원되는지.

를 시험합니다. 지원하지 못하는 형식은 **조용히 텍스트로 낮추지 않고 표시**합니다.

## 비정상 종료 대비

SQLite는 다음을 사용합니다.

- **WAL**
- **`synchronous=FULL`**
- 단일 쓰기 작업자
- 버전별 마이그레이션

저장 순서는 다음과 같습니다.

1. 원본을 임시 파일에 기록하고 flush.
2. 최종 불변 파일 이름으로 변경.
3. DB 트랜잭션으로 항목과 참조를 확정.
4. 그 뒤 “저장 완료” 상태로 표시.

DB 확정 전에 죽어 남은 고아 파일은 나중에 정리합니다.

이 방식은 **저장 완료된 히스토리를 프로세스 비정상 종료에서 보호**합니다. 복사가 일어난 바로 그 순간부터 저장이 끝나기 전까지의 내용이나, 저장 장치가 flush를 지키지 않는 상황까지 무손실을 보장할 수는 없습니다.

## 용량·메모리 정책

- 50~500개는 화면에서 참조하는 항목 수이지, 원본을 전부 RAM에 올리는 수가 아님.
- 원본은 지연 로딩.
- 썸네일은 바이트 기준 LRU 캐시.
- 순차 줄의 다음 항목은 미리 준비하되 크기 상한 적용.
- 히스토리에서 빠져도 고정·메모·순차 줄이 참조하면 원본 유지.
- 삭제 후 파일 정리는 지연 수행.

이미지 경로 붙여넣기는 `exports` 아래 안정된 PNG 파일을 만들고 **경로 문자열을 시스템 클립보드에 올리는 별도 표현 방식**입니다. 원본 히스토리는 변경하지 않습니다. 파일을 너무 빨리 지우지 않도록 보존 기간과 명시적 정리를 제공합니다.

메모 일괄 삭제는 즉시 물리 삭제하지 않고 삭제 묶음을 기록하여 되돌립니다. 자동 저장은 짧은 debounce와 창 전환 시 flush를 사용하며, 저장되지 않은 마지막 입력의 허용 범위를 별도로 정의합니다.

**2등:** 모든 원본을 SQLite BLOB에 저장. 초기 구현과 백업은 더 단순합니다. 데이터가 작다면 좋지만, 큰 이미지와 파일 접근·내보내기가 잦은 이 도구에서는 별도 파일을 택합니다.

# 5. 시험과 검사

## 첫 구현물은 전체 화면이 아니라 입력·클립보드 시험기입니다

먼저 작은 프로그램으로 다음만 검증합니다.

- A/B/C 복사와 순차 붙여넣기.
- 일반 Ctrl+V 통과.
- 한국어 IME 팝업 방지.
- 실제 사용하는 앱의 원본 형식 복원.
- 키를 누른 채로 유지하거나 아주 빠르게 반복할 때의 동작.

이 검증을 통과하기 전에 전체 UI를 만들지 않습니다.

## 순차 붙여넣기 구현 계약

### 키 감지와 주입

핵심 단축키는 **`WH_KEYBOARD_LL`**, 주입은 **`SendInput`**을 사용합니다.

- 훅 콜백에서는 키 상태 기록·판정·작업 요청만 수행.
- 클립보드 접근, 디스크, UI, 네트워크 호출 금지.
- Ctrl+Shift+V의 단축키 V down/up과 반복을 일관되게 처리.
- 도구 입력에는 `dwExtraInfo` 식별값을 붙임.
- 자기 입력을 일반 Ctrl+V 관찰에서 제외.
- 다른 프로그램이 넣은 입력을 전부 자기 입력처럼 무시하지 않음.

클립보드를 교체한 뒤 대상 창과 실제 키 상태를 다시 확인하고, 필요한 modifier 해제·Ctrl+V·상태 복구를 수행합니다. 왼쪽/오른쪽 Ctrl·Shift를 구분하고, 작업 중 사용자가 키를 놓은 경우 **오래된 상태로 다시 눌러 놓지 않도록** 합니다.

`SendInput` 성공은 대상 앱이 붙여넣기를 실제로 완료했다는 뜻이 아닙니다. 진행 위치는 입력 전달 결과에 따라 관리하고, 실패 시 무조건 재시도하여 중복 붙여넣기를 만들지 않습니다.

### IME

Ctrl·Shift 이벤트는 V가 눌리기 전에 이미 대상 앱에 전달되었을 수 있습니다. 따라서 **V를 삼키는 것만으로 IME 팝업까지 막힌다고 가정하지 않습니다.**

modifier를 잠시 해제할 때의 이벤트 순서와 IME의 조합키 판정을 별도로 시험합니다. Windows 버전·한국어 IME 설정별로 검증된 순서를 계약으로 고정합니다. 평범한 Ctrl+Shift 사용까지 항상 가로막는 편법은 쓰지 않습니다.

### 큐 소진 시의 해석

명세에는 한 가지 정리가 필요합니다.

- “개입하지 않는다”를 키까지 완전히 통과시킨다는 뜻으로 보면, Ctrl+Shift+V는 대상 앱마다 다른 기능이므로 마지막 항목이 계속 붙는다고 보장할 수 없습니다.
- 저는 **큐와 클립보드는 더 이상 바꾸지 않되, 단축키를 깨끗한 Ctrl+V로 바꾸는 동작은 유지**하는 계약을 선택하겠습니다.

이 해석을 개발 전에 확정하겠습니다.

### 자기 클립보드 쓰기 제외

`AddClipboardFormatListener`와 `GetClipboardSequenceNumber`를 사용합니다. 자기 쓰기는 쓰기 세대·클립보드 소유자·내부 표식 등을 함께 추적합니다.

단순히 “다음 알림 한 번 무시”하지 않습니다. 그 사이 외부 복사가 끼거나 알림이 합쳐질 수 있기 때문입니다.

## 자동 시험 목록

| 영역 | 시험 |

| 이벤트 순서 | 복사와 붙여넣기 동시 발생, 연타, 키 반복, 취소, 대상 창 변경 |

## Windows 부분 시험

자체 시험 대상 앱을 만듭니다.

- 전달받은 키 이벤트·전경 창 기록.
- 실제 요청한 클립보드 형식 기록.
- 클립보드를 일부러 오래 점유.
- 지연 렌더링 데이터 제공.
- 읽기 도중 원본 앱 종료.

일반 CI에서는 순수 로직·저장 시험을 돌리고, 전역 키·IME·초점 시험은 **로그인되고 잠금이 풀린 전용 Windows 시험 환경**에서 돌립니다. 실제 한국어 IME 팝업과 일부 앱 전용 동작은 짧은 수동 회귀 시험도 남겨 둡니다.

## 성능 기준

- 복사 감지 100ms: **OS 알림 수신부터 내부 이벤트 등록까지**와 **원본 저장 완료까지**를 분리 측정.
- 클립보드 교체 50ms: 대상 크기를 명시하고 정상 경로 p95·p99 측정.
- 클립보드 점유 시: 무한 대기하지 않고 짧은 재시도 후 실패 표시.
- 대기 메모리: 모든 상주 프로세스 합산.
- 대기 CPU: 트레이 상태에서 수분 이상 측정.
- 시작 3초: 런타임·DB 초기화가 끝나 단축키를 받을 수 있는 시점도 함께 측정.

검사에는 **ASan, clang-tidy, `/analyze`, Application Verifier**, 성능 분석에는 **ETW/WPA**를 사용합니다.

80MB는 계획만으로 달성했다고 하지 않습니다. 최대 히스토리를 가진 실사용 데이터로 릴리스 승인 조건을 걸겠습니다.

# 6. 배포

## 선택: 자체 포함 설치 폴더 + Inno Setup 단일 EXE

빌드는 다음으로 고정합니다.

- CMake Presets.
- vcpkg baseline.
- MSVC·Windows SDK·Qt 버전.
- Release x64 빌드.
- `windeployqt`로 필요한 DLL·플러그인 수집.
- 불필요한 Qt 모듈 제외.

배포물은 **Inno Setup으로 만든 EXE 하나**입니다.

설치 위치:

```text
%LOCALAPPDATA%\Programs\PersonalHub\
```

데이터는 설치 폴더 밖에 두므로 업데이트·재설치로 없어지지 않습니다.

앱 파일 자체를 억지로 하나로 합치기보다, **사용자가 받는 파일 하나**를 택합니다. DLL 자가 추출 방식의 단일 실행 파일은 시작 시간·보안 제품 오탐·문제 추적에서 이득이 적습니다.

## 권한과 자동 실행

- 기본적으로 일반 사용자 권한으로 실행.
- 자동 시작은 HKCU `Run` 또는 사용자 시작프로그램 항목.
- 단일 인스턴스는 named mutex.
- 관리자 권한 앱에 대한 `SendInput`은 UIPI 때문에 막힐 수 있음을 표시.

기본 앱 전체를 관리자 권한으로 돌리는 방식은 선택하지 않습니다. 꼭 필요한 관리자 앱이 있다면 별도 요구로 다루고, 권한 있는 보조 프로세스의 좁은 인터페이스를 검토합니다.

단축키 충돌은 일반 조합에는 `RegisterHotKey` 등록 시험을 사용합니다. 단, 다른 앱의 저수준 훅이나 앱 내부 단축키까지 완전하게 알아낼 수는 없으므로 **검출 가능한 충돌과 검출 불가능한 충돌을 구분**합니다.

## 3~4대 업데이트

처음에는 복잡한 자동 업데이트 서버를 만들지 않습니다.

1. 시험을 통과한 설치 파일과 버전 정보를 한 릴리스 폴더에 게시.
2. 앱에서 하루 한 번 정도 새 버전 확인.
3. 사용자가 승인하면 다운로드.
4. 녹화·붙여넣기 등 진행 중 작업이 끝난 후 종료.
5. DB 백업 후 설치.
6. 실패하면 직전 앱 버전으로 복귀.

사내 SMB 공유나 비공개 HTTPS 저장소면 충분합니다. 무결성용 SHA-256과 별도로 **신뢰할 수 있는 배포 경로 또는 서명된 manifest**를 사용합니다. 해시만으로는 공격자가 바꾼 업데이트를 판별할 수 없습니다.

직전 실행 파일과 DB 백업을 남기되, **DB 스키마가 바뀐 경우 실행 파일만 되돌리지 않습니다.**

3~4대 중 한 대에 먼저 업데이트하고 하루 사용한 뒤 나머지에 배포하는 방식이 비용 대비 효과가 큽니다.

**2등:** ZIP 포터블 배포. 가장 빨리 시작할 수 있지만, 실행 중 덮어쓰기·자동 시작 경로·롤백 관리가 불편해 장기 운영에는 설치 파일이 낫습니다.

# 가장 위험한 기술 지점 세 곳

## 1. 키 가로채기·modifier 복원·한국어 IME

**위험:** 한 번의 타이밍 오류가 중복 붙여넣기, 잘못된 창 입력, Shift가 눌린 상태로 남는 문제를 만듭니다.

**대응:**

- 전체 앱보다 먼저 독립 시험기 제작.
- 훅 콜백에서 모든 무거운 작업 금지.
- 자기 입력 식별과 단축키 down/up 처리 계약 고정.
- 실제 키 상태와 대상 창을 재확인.
- IME·좌우 modifier·연타·중간 키 해제 회귀 시험.
- 실패 시 잘못 붙이기보다 취소하고 알리기.

## 2. 클립보드 원본 형식 보존과 50ms 교체

**위험:** 형식은 남았어도 붙여넣기 결과가 달라지거나, 지연 렌더링·클립보드 잠금 때문에 멈출 수 있습니다.

**대응:**

- 형식별 스냅샷과 복원 어댑터.
- 실제 사용하는 앱 중심의 호환성 목록.
- 다음 항목 사전 준비와 크기 제한된 캐시.
- 자기 쓰기·외부 쓰기 경합 시험.
- 직렬화 불가능한 형식은 명시적으로 표시.
- 정상 경로 성능과 외부 앱 때문에 지연되는 경우를 분리.

## 3. 다중 모니터·혼합 DPI·장시간 녹화

**위험:** 선택 영역과 실제 픽셀이 어긋나거나, 녹화 시간이 길수록 메모리가 늘거나, 종료 시 영상 전체가 손상될 수 있습니다.

**대응:**

- 물리 픽셀 좌표계를 핵심 계약으로 통일.
- 모니터별 캡처·합성 분리.
- UI Automation 조회를 캡처 조작 경로에서 분리.
- 유한 버퍼와 명시적인 프레임 드롭 정책.
- 파일 스트리밍과 fragmented MP4 검증.
- 디스크 부족·장치 변경·강제 종료 시험.
