# 260713_구글드라이브 검색 연동 계획

AI 질의가 **내 구글 드라이브 문서를 근거로** 답하게 한다. 게이트웨이 Responses API가
중계하는 OpenAI 커넥터(`connector_googledrive`)를 검색 심부름꾼에 얹는 방식.

**현재 상태: 1·2·3단계 전부 완료·실조건 검증됨(2026-07-14).** 앱에서 실제로 동작한다 —
설정창에서 드라이브를 연결하면 AI 질의가 내 드라이브 문서를 근거로 답한다.
남은 것은 기능 추가가 아니라 **검색 품질 튜닝**이다(아래 「남은 과제」).

---

## 실호출로 검증된 사실 (2026-07-13)

추측이 아니라 실제로 던져 보고 확인한 것들이다. 다시 검증할 필요 없다.

- **게이트웨이가 `mcp` 커넥터 도구를 중계한다.** Mindlogic 게이트웨이
  (`https://factchat-cloud.mindlogic.ai/v1/gateway`)의 Responses API에 아래 도구를 실어
  보내면 `mcp_list_tools`로 드라이브 도구 목록이 오고 `mcp_call`이 실제로 실행된다.

  ```python
  tools=[{
      "type": "mcp",
      "server_label": "gdrive",
      "connector_id": "connector_googledrive",
      "authorization": "<구글 OAuth 액세스 토큰>",
      "require_approval": "never",
  }]
  ```

- **진짜 토큰이면 실제 드라이브 파일명이 돌아온다** (OAuth Playground에서 받은
  `drive.readonly` 토큰으로 확인 — `recent_documents` 호출 → 실제 파일 3건 반환).
  가짜 토큰일 때는 같은 호출이 `http_error 500`으로 실패했다. 즉 **중계 + 인증 경로 모두 정상.**

- **커넥터는 읽기 전용**: `search` / `fetch` / `recent_documents` / `list_drives`.
  스코프는 `https://www.googleapis.com/auth/drive.readonly` 하나면 된다. 쓰기·수정은 불가.

- **액세스 토큰은 1시간 만료** → refresh token 흐름이 필수다(이게 이 기능의 실제 작업량 대부분).

- **~~공식(AI Studio) 백엔드는 이 기능을 못 쓴다~~ → 무의미해짐(v1.50.0).** 원래는 공식 백엔드에
  커넥터 통로가 없어 "게이트웨이 전용 기능"이라는 제약이 있었는데, v1.50.0에서 **공식 백엔드
  자체가 제거**돼(게이트웨이 단일 경로) 이 제약이 사라졌다. 이제 커넥터 방식이 유일한 경로이자
  전 모델에 적용되는 방식이다 — 아래 설계는 그대로 유효하다.

---

## 설계 — 삽입점은 "도구 목록에 한 줄"

게이트웨이 AI 질의의 검색은 세 갈래인데, 셋 다 `tools=[...]`를 넘기는 지점이 있다.
거기에 `gdrive.drive_tool(token)`을 **하나 더 넣기만** 하면 된다.

| 경로 | 지금 | 드라이브 추가 지점 |
|---|---|---|
| GPT 모델 | Responses 내장 web_search | `ocr_engine._ask_openai_responses`의 `tools` |
| 그 외 모델 (claude·gemini…) | 도구 왕복 → `web_search.search()` → nano | `web_search._search_via_gpt`의 `tools` |
| 여러 모델 비교 | `web_search.prefetch()` → nano | `web_search.prefetch`의 `tools` |

**핵심:** 비GPT 모델은 자기가 검색하는 게 아니라 **nano 심부름꾼에게 시킨다.** 그래서 nano에
드라이브를 쥐여 주면 claude·gemini도 그대로 드라이브를 검색하게 된다 — 모델별 도구 호환성
지뢰(Llama-4-Maverick의 `tools` → 405, Gemini 3의 `thought_signature` 에코백 등)를 다시
밟지 않는 것이 이 방식의 진짜 이득이다.

**발동 정책(결정됨):** 질문창 체크박스 같은 옵트인 없이 **항상 도구로 제공하고 모델이 판단**한다
(웹 검색과 동일한 게이트키퍼 구조). 토큰이 없으면 도구만 조용히 빠진다(우아한 열화).

## 남은 과제 — 검색 **품질** (기능은 끝났다)

2026-07-14 실측으로 병목이 어디인지 갈렸다. **커넥터는 충분하다. 심부름꾼(nano)이 약하다.**

- **커넥터는 본문까지 본다(확정)**: 파일명엔 없고 PRD.md 본문에만 있는 문구
  (`제로 설정`·`노션 호환`)로 `search`가 그 문서를 정확히 찾았고, `fetch`가 **본문 전체를 반환**했다.
  즉 구글 드라이브 웹 검색과 같은 전문(full-text) 색인을 쓴다. "커넥터는 파일명만 본다"는 추측은 **오답**이었다.
- **자료를 받고도 모델이 못 쓴다**: 같은 질문·같은 도구로 지시문만 바꾸자 ⓐ 지시문 없음 → 문서는 찾고
  **표 내용을 환각**(실제 PRD에 없는 항목을 창작) ⓑ 현행 지시문 → "표는 확인 안 됨"으로 정직하게 포기
  ⓒ 엄격 지시문 → "못 찾음". 세 경우 다 `search`+`fetch`는 정상 수행됐다.
- **그래서 후보**: 심부름꾼 모델 격상(`gpt-5.4-nano` → `gpt-5.4-mini`, 단 옛 웹검색 실측에서 mini는
  51~83초로 느렸다) / 드라이브를 쓰는 질문일 때만 조건부 격상 / `fetch` 결과를 요약하지 말고
  본문을 그대로 본 모델에 넘기기. **실측 비교 후 결정할 일이며, 아직 아무것도 정하지 않았다.**
- ⏳ **미검증**: 이미지·PDF 속 글자(구글이 OCR해 색인)를 커넥터가 찾아 주는지 — 검증할 이미지가 없어 못 했다.

**참고**: GPT 모델을 AI 모델 1로 쓰면 심부름꾼을 **거치지 않고** 그 모델이 직접 드라이브를 검색한다
(Responses 경로). 즉 위 병목은 비GPT 모델(gemini·claude)에서 더 크게 나타난다.

## 후속 (2026-07-14 · v1.52.0) — 브라우저 경로가 이 병목을 우회한다

이 문서의 「남은 과제」(심부름꾼 nano가 자료를 받고도 못 읽어 환각)는 **API 경로에서는 여전히 열려 있다.**
그러나 같은 날 **브라우저 경로**(`pasteflow/web_open.py`)가 들어와, 사용자가 실제로 쓰는 길이 갈렸다.

- **드라이브 검색**: 질문창 `드라이브` 버튼 → `drive.google.com/drive/search?q=…`를 **크롬에서 그대로 연다**.
  크롬 로그인 세션을 타므로 OAuth·토큰·커넥터가 **하나도 필요 없고**, 심부름꾼 독해 품질 문제도 없다
  (사람이 직접 본다). 대신 답을 프로그램이 못 받아 온다.
- **그래서 이 문서의 격상 결정(nano→mini)은 우선순위가 내려갔다.** API 드라이브 연동은 "AI가 내 문서를
  근거로 답해야 할 때"만 남고, 단순히 "내 드라이브에서 찾기"는 브라우저가 더 빠르고 정확하다.
- ⏳ **아직 지우지 않았다** — API 배관(커넥터·TokenCache·설정창 그룹)은 그대로 둔다. 며칠 써 보고
  실제로 안 쓰면 그때 철거 여부를 판단한다(되돌리기 비싼 삭제는 판단 재료가 쌓인 뒤에).
