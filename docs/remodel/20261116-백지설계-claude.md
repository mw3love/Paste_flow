## 1. 언어

**고를 것: C# (.NET 8 LTS)**

이 도구는 Windows 깊은 곳을 많이 건드립니다. 전역 키 감지, 클립보드 형식, 다른 창의 부품 경계, 화면 녹화, 마이크가 그렇습니다. C#은 이 영역을 다루는 기능이 거의 다 있습니다. `user32` 호출은 CsWin32가 자동으로 만들어 주는 연결 코드로 쓰고, 클립보드는 `AddClipboardFormatListener`로 지켜봅니다. 창 부품은 UI Automation(`System.Windows.Automation` 또는 COM `IUIAutomation`)으로 읽고, 화면 캡처는 Windows.Graphics.Capture로 합니다. 마이크는 NAudio나 WASAPI로 받습니다. AI가 학습한 예제도 가장 많습니다. 타입 검사가 엄격해서 AI가 실수하면 컴파일 단계에서 걸러지는 점도 이 사용자에게 잘 맞습니다.

- 2등: Rust (`windows` 크레이트 + Tauri 등).
- 2등이 나은 경우: 메모리 80MB 미만과 CPU 0.5% 미만이 C#으로 안 맞을 때(.NET 런타임이 올라가면 보통 40~70MB입니다). 또는 설치 파일 크기와 시작 속도가 가장 중요해질 때. 컴파일러 오류가 엄격해서 AI 수정 반복이 늘어나는 비용은 감수해야 합니다.

비교한 다른 후보입니다.
- Python: 키보드·클립보드 후킹은 쉽지만 상주 메모리 80MB 미만이 어렵고 배포 파일이 큽니다.
- Electron/Node: 메모리 예산을 혼자 다 씁니다.

## 2. 화면 도구

**고를 것: WPF (.NET 8) + MVVM(CommunityToolkit.Mvvm)**

이유는 다음과 같습니다.

- 포커스를 빼앗지 않는 창이 필요합니다. WPF는 `WS_EX_NOACTIVATE`와 `ShowActivated=false`를 창 단위로 줄 수 있습니다.
- 패널, 설정창, 번호표 오버레이, 주석 편집기를 모두 XAML 컨트롤로 만들고 다시 쓰기 쉽습니다. 화면을 자주 바꾸는 사정과 맞습니다.
- 주석 편집기는 `InkCanvas`와 벡터 도형 레이어로 만들 수 있습니다. 투명한 전체 화면 오버레이(영역 선택)도 지원됩니다.
- 다중 모니터와 DPI는 `PerMonitorV2` 매니페스트로 대응합니다.
- 어두운 테마와 고대비는 ResourceDictionary를 바꾸는 것으로 처리합니다.
- 트레이 아이콘은 `H.NotifyIcon.Wpf`를 씁니다.

- 2등: WinUI 3 (Windows App SDK).
- 2등이 나은 경우: 모양이 Windows 11 네이티브처럼 보이는 것이 중요해질 때. 다만 NOACTIVATE 창, 오버레이, 비패키지 배포에서 아직 까다로운 부분이 많아서, 지금은 WPF가 더 안전합니다.

비교한 다른 후보입니다.
- Qt(C++ 또는 Python): 크로스 플랫폼이 필요 없는데 라이선스와 크기 부담이 있습니다.
- WebView 기반(Tauri 등): 포커스 제어와 오버레이가 까다롭습니다.

## 3. 폴더 구조

**고를 것: 솔루션 하나를 층별 프로젝트로 나누고, 그 안은 기능별 폴더로 나눕니다.**

```
/src
  Core/           순수 로직. Windows 의존 없음 (순차 붙여넣기 상태 기계, 큐 규칙, 히스토리 정책)
  Platform/       Windows 연결부. 인터페이스 뒤에 숨김 (IClipboardGateway, IKeyHook, IWindowProbe, IScreenCapture, IMic)
  Features/       기능별 폴더 (SequentialPaste, Panel, Capture, Recorder, Annotate, Ocr, Voice, Memo, Settings)
  App/            WPF 셸. 시작, 트레이, DI 구성 (Microsoft.Extensions.DependencyInjection)
/tests
  Core.Tests/  Platform.Tests/(수동 표시)  Architecture.Tests/
```

- 핵심 규칙은 「Core는 Platform을 모른다」입니다. 순차 붙여넣기 타이밍 규칙은 Core의 상태 기계(시계와 이벤트를 주입)로 만듭니다. 그러면 운영체제 없이도 시험할 수 있습니다. 앞서 두 번 실패한 부분이 바로 여기라서 가장 중요한 구조입니다.
- 큰 파일 방지는 사람의 감시가 아니라 기계가 합니다. 파일당 300줄을 넘으면 빌드가 실패하게 합니다(`.editorconfig` 분석기 규칙이나 CI 스크립트). 층 간 참조 규칙은 NetArchTest로 시험합니다.
- 기능 폴더 하나는 AI 한 번의 작업 범위가 되도록 작게 유지합니다.

- 2등: 기능별 프로젝트 분리(기능마다 csproj).
- 2등이 나은 경우: 기능이 열 개를 훨씬 넘어 빌드 시간이 길어질 때. 지금 규모에서는 프로젝트 수가 늘어 AI가 헷갈리는 비용이 더 큽니다.

## 4. 데이터 저장

**고를 것: SQLite 한 파일(히스토리·고정·메모) + JSON 설정 파일 + 이미지는 파일로 따로.**

- 위치는 `%LOCALAPPDATA%\AppName\`입니다.
- `history.db`는 `Microsoft.Data.Sqlite`로 쓰고 WAL 모드를 켭니다. 비정상 종료에도 트랜잭션 단위로 안전해서 "히스토리를 잃지 않는다"를 맞춥니다. 항목 표에는 id, 종류, 시각, 고정 여부와 순서, 미리보기 글자를 둡니다.
- 서식 있는 항목은 형식별 바이트 묶음(HTML, RTF, 앱 전용 형식 이름과 바이트)을 `item_formats` 표에 담습니다. 원래 형식을 되살려 붙이려면 형식 이름 그대로 저장해야 합니다.
- 큰 바이트와 이미지는 `blobs\<해시>.png`로 저장하고 DB에는 경로와 해시만 둡니다. 해시가 같으면 한 번만 저장해서 DB가 부풀지 않습니다. 개수 제한(10~500)을 넘은 것은 고정 항목을 빼고 삭제하고, 파일은 정리 작업이 지웁니다.
- 설정은 `settings.json`(`System.Text.Json`)입니다. 사람이 열어 볼 수 있고 PC 간에 복사하기 쉽습니다.
- API 키는 `ProtectedData`(DPAPI, CurrentUser 범위)로 암호화한 값을 따로 저장합니다. 설정 JSON에 평문으로 넣지 않습니다.
- 2등: 전부 JSON 파일. 나은 경우는 고정 항목이 수십 개 이하이고 히스토리를 저장하지 않아도 될 때입니다. 항목 수정이 잦아지면 파일 전체 덮어쓰기가 깨질 위험이 있습니다.

## 5. 시험과 검사

**고를 것: 층마다 다른 시험을 씁니다.**

- **Core:** xUnit과 FluentAssertions로 단위 시험을 합니다. 순차 붙여넣기 큐 규칙(새 복사로 비움·10초 경과·평범한 Ctrl+V·소진 뒤 개입 안 함·자기가 쓴 클립보드를 무시)을 모두 가짜 시계로 시험합니다. 속성 기반 시험(FsCheck)으로 임의 순서의 이벤트에도 규칙이 깨지지 않는지 봅니다.
- **Platform:** 인터페이스의 가짜 구현으로 Features를 시험하고, 진짜 구현은 얇게 유지합니다. 진짜 클립보드, 진짜 키 입력은 별도 통합 시험으로 합니다. Windows 러너에서 메모장을 띄우고 `SendInput`으로 Ctrl+Shift+V를 보낸 뒤 결과 글자를 읽어 확인합니다. 이 시험은 실제 데스크톱이 필요하므로 만든 사람의 PC에서 스크립트 한 줄로 돌립니다.
- **화면:** ViewModel을 시험합니다. 화면 모양은 Verify 스냅샷(스크린샷 비교)이나 FlaUI 같은 UI 자동화로 핵심 흐름만 봅니다.
- **정적 검사:** Roslyn 분석기, `TreatWarningsAsErrors`, nullable 활성화, 파일 길이 제한, NetArchTest 층 규칙을 모두 빌드에 넣습니다. 커밋 전 훅이나 GitHub Actions에서 자동으로 돌립니다.
- **성능 예산:** 메모리·시작 시간·복사 감지 지연을 재는 스모크 시험을 두고 기준을 넘으면 실패시킵니다.

- 2등: 단위 시험만 하고 통합은 손으로 확인합니다.
- 2등이 나은 경우: 사용자가 매번 직접 써 보는 비중이 크고 시험 유지 비용이 부담될 때. 하지만 이 도구는 키 타이밍 회귀가 반복될 위험이 커서 통합 시험을 하나라도 두는 쪽이 낫습니다.

## 6. 배포

**고를 것: 자기 완결형 단일 실행 파일 + Velopack으로 자동 업데이트.**

- 빌드는 `dotnet publish -c Release -r win-x64 --self-contained -p:PublishSingleFile=true`입니다. 사용자 PC에 .NET을 따로 설치하지 않아도 됩니다. 시작 속도 때문에 ReadyToRun 옵션도 켭니다. 크기가 크면 trimming은 WPF에서는 위험하니 쓰지 않습니다.
- Velopack으로 설치 파일 하나(`Setup.exe`)와 업데이트 묶음을 만들고, GitHub Releases의 비공개 저장소나 사내 공유 폴더에 올립니다. 앱이 시작할 때 새 버전을 확인하고 다음 실행에 적용합니다. PC 3~4대는 한 번 설치하면 그다음부터는 자동으로 따라옵니다.
- 시작 프로그램 등록은 `HKCU\...\Run` 키로 하고, 서명은 하지 않습니다(혼자 쓰므로). SmartScreen 경고는 처음 한 번만 넘기면 됩니다.
- 빌드와 릴리스는 스크립트 하나(`build.ps1`)로 만들어 AI가 실행하게 합니다.

- 2등: MSIX 패키징.
- 2등이 나은 경우: 인증서를 만들어 쓸 의향이 있고 깨끗한 설치·제거를 중요하게 볼 때. 서명 인증서 관리 부담 때문에 지금은 Velopack이 낫습니다.
- 또 다른 2등: 압축 파일만 공유 폴더에 두고 수동 교체. 나은 경우는 PC가 두 대 이하로 줄고 자동 업데이트가 필요 없을 때입니다.

## 가장 위험한 기술 지점 세 곳

**1. 붙여넣기 키를 막지 않는 순차 붙여넣기 (타이밍)**

앞서 두 번 실패한 지점입니다. 키 감지는 `WH_KEYBOARD_LL` 저수준 후크로 합니다. 후크 함수 안에서는 키를 막지 않고, 클립보드 교체만 아주 짧게 시작해야 합니다. 후크가 느리면 Windows가 후크를 해제해 버리므로, 후크 콜백은 큐에 이벤트만 넣고 바로 돌아옵니다. 클립보드 쓰기는 전용 스레드에서 합니다.

주의할 점이 두 가지 있습니다. 하나는 키가 눌린 뒤 대상 앱이 클립보드를 읽는 시점보다 교체가 늦으면 이전 항목이 붙는다는 점입니다. 다른 하나는 도구가 쓴 클립보드 변경을 새 복사로 착각하는 일입니다. 이를 막으려면 쓰기 직전 `GetClipboardSequenceNumber` 값을 기억해 두고, 자기가 일으킨 변경 알림은 번호로 구별해 무시합니다. 또 다른 클립보드 도구와의 충돌과 클립보드가 다른 프로세스에 잠겨 있을 때의 재시도(짧은 간격, 몇 번까지만)도 정해 둡니다. 시험은 5절의 메모장 통합 시험을 매 변경마다 돌리고, 지연이 50ms를 넘으면 실패 처리합니다.

**2. 클립보드 형식 전체를 원래대로 저장하고 되살리기**

앱 전용 형식(노션 등)은 지연 렌더링이라서, 복사한 앱이 요청 시점에만 내용을 만들어 주는 경우가 있습니다. 또 비트맵(DIB·DIBV5·PNG)이 여러 형태로 동시에 있고, 핸들 종류(HGLOBAL, 스트림, 메타파일)도 제각각입니다. 모든 형식을 열거해 즉시 읽고 바이트로 보관하며, 읽을 수 없는 형식은 건너뛰되 기록은 남깁니다. 복사 직후 바로 읽어야 앱이 종료되어도 잃지 않습니다. 용량 상한(예: 형식당 50MB)을 두고 초과하면 텍스트와 대표 이미지만 저장합니다. 시험은 노션·엑셀·워드·브라우저에서 복사한 실제 샘플을 사 둔 고정 시험 자료(골든 파일)로 저장·복원 왕복을 비교합니다.

**3. 포커스를 빼앗지 않는 창과 화면 캡처·녹화**

패널이 포커스를 가져가면 대상 앱에서 붙여넣기가 안 됩니다. `WS_EX_NOACTIVATE`, `ShowActivated=false`, 클릭 처리 때 `WM_MOUSEACTIVATE`를 `MA_NOACTIVATE`로 응답하는 처리를 모두 해야 하고, 패널 안의 텍스트 입력(검색·메모)에서만 일시적으로 활성화를 허용해야 합니다. 화면 쪽에서는 여러 모니터의 DPI가 서로 다를 때 좌표 변환이 어긋나기 쉽고, 창 안 부품 경계(UI Automation)는 앱마다 응답 속도가 달라서 느린 앱 때문에 선택 화면이 멈출 수 있습니다. UI Automation 조회에는 제한 시간(예: 50~100ms)을 두고 별도 스레드에서 처리하며, 시간이 지나면 창 경계만 씁니다. 녹화는 Windows.Graphics.Capture를 쓰고 프레임을 ffmpeg 파이프나 Media Foundation 인코더로 파일에 바로 흘려 써서 메모리를 쌓지 않습니다. 다중 모니터·DPI 혼합 환경의 좌표 변환은 Core에 순수 함수로 두고, 모니터 배치 몇 가지를 표로 만들어 단위 시험합니다.
